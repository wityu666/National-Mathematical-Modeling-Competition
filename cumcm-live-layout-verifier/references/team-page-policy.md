# 团队正文页数配置

26–30 页是套件的兼容默认配置，不是对所有团队的强制要求，也不表示新用户已经确认。任务中已有的页数选择继续有效；新任务从用户要求或团队声明记录选择，不为日常执行重复询问。

通过比赛工作目录中的 JSON 文件声明其他正文区间：

```json
{
  "schema_version": 1,
  "policy_id": "team-18-24",
  "rationale": "本队根据题目规模选择正文 18–24 页。",
  "min_main_pages": 18,
  "max_main_pages": 24
}
```

- 五个字段都必须存在；未知键、重复键、空理由、非整数和倒置区间均拒绝。
- 只调整正文页数偏好；不能关闭真实性、每问实质答案、独立复核、Word/PDF 一致性、正文边界或附录关键代码检查。
- 命令使用 `--team-policy /比赛工作目录/team-page-policy.json`；不要与旧版 `--min-main-pages/--max-main-pages` 混用。
- 官方限制单独登记：`--official-max-main-pages 20 --official-page-rule '官方通知第 X 条及来源'`。工具采用团队上限与官方上限的较小值；官方上限低于团队下限时将内部下限降为 1。来源文字是操作者提供的证据入口，脚本不会替代查证官方文件。
- 官方“全文总页数”限制不能冒充“编号正文页数”限制；总页数等其他规定继续由官方规则矩阵单独核验。
- 不传团队配置时保留原 26–30 页和旧版 CLI 行为，以兼容已冻结任务；旧版参数不应被当作无记录放宽内部要求的入口。

例如，下列命令从实际 PDF 读取总页数，并使用本队区间检查正文：

```bash
python3 scripts/layout_preflight.py /比赛工作目录/final.pdf \
  --source /比赛工作目录/final.docx \
  --team-policy /比赛工作目录/team-page-policy.json \
  --abstract-end-page 1 --main-start-page 2 \
  --appendix-start-page 22 --appendix-code-page 22 --json
```

页码只是命令示意，必须替换为本次 PDF 中实际查证的物理页码。该示例正文为 20 页。

预检报告的 `page_policy` 保存配置 ID、绝对路径、从实际读取字节计算的 SHA-256、声明的区间、官方限制来源和最终有效区间。默认路径标为 `legacy_default`，旧参数标为 `legacy_cli`，显式文件标为 `team_policy`。报告的 `page_limit` 使用有效区间计算。

问题合同、论文事实表、LAYOUT 和终审记录传递同一 `policy_id/source/sha256` 及有效区间。续做时重新核对该文件的哈希；配置变化使旧页数判断、排版报告与终审失效，必须重新检查。没有更改的数学结果不因页数偏好变化而重跑。

文档中未显式标注配置的 26–30 页公式、目标和示例均指兼容配置；使用团队配置时，以登记的有效区间替换这些常量。不存在“少于 26 页就必然缺乏深度”的结论，内容是否充分仍按每问答案与证据判断。配色选择和双版本交付继续按各自既有合同执行。
